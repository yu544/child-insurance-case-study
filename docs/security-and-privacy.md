# 安全与隐私设计

这个项目处理未成年人敏感数据，安全设计是产品主线的一部分。

## 数据与威胁模型

| 数据 | 风险 | 措施 | 对应样例 |
| --- | --- | --- | --- |
| 儿童姓名 | 数据库泄露后可直接识别个人 | AES-256-GCM 字段加密，前端脱敏展示 | `src/field-crypto` |
| 身份证号 | 高敏身份信息，泄露影响严重 | 加密存储，HMAC 盲索引用于查重 | `src/field-crypto` |
| 监护人手机号 | 可被骚扰或用于撞库 | 加密存储，默认只展示掩码 | `src/field-crypto` |
| 人脸资料照 | 生物识别敏感数据 | 私有对象存储，前端不暴露永久公开 URL | `docs/cloud-procurement-rationale.md` |
| 投保订单 | 状态错误会导致孩子无保障 | 显式状态机、卡单检测、对账兜底 | `src/insurance-state-machine` |
| 门店主体 | 投保主体错误会影响理赔 | 按门店解析主体，缺失则拒绝投保 | `docs/product-overview.md` |

## 核心原则

### 1. 前端不持有密钥

人脸识别、对象存储和保险平台都通过后端转发。前端只调用业务 API，不直接持有云厂商或保险平台密钥。

### 2. 数据库不保存可直接检索的明文身份证号

身份证号加密后不可直接查重，所以引入 HMAC 盲索引。系统能判断“这个证件号是否已存在”，但数据库泄露者不能从索引反推出原文。

### 3. 图片默认私有

资料照不放公网目录，不把图片二进制塞数据库，也不把永久 URL 直接给前端。前端访问图片应由后端生成短期地址或代理读取。

### 4. 识别结果不等于业务事实

人脸识别返回的是候选，不是最终身份。系统要求教练看到脱敏资料后人工确认，再进入投保。

### 5. 安全要能被验证

项目上线前邀请网络安全工程师进行渗透尝试，并基于结果加固服务器登录、云账号权限、备份策略和公网入口。简历与作品集只描述安全措施，不公开攻击细节和生产配置。
